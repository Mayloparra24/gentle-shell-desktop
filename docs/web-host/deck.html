The problem

Why a web host

It removes the packaging step from the path to a first chat

Today you run the app from source with Electron. There are no signed builds, and only macOS on Apple silicon has been tested (README.md, "Try it"). A browser host needs Node and the launcher the user already has.

It helps contributors verify real behavior

ADR 0010 already runs the renderer in a browser, but against a mock bridge. The web host runs it against real sessions.

It makes the Windows launcher problem visible from a second angle

On Windows an npm-installed gentle-shell resolves to gentle-shell.cmd, which Node cannot spawn directly. That is issues #23 and #24, and it blocks both hosts equally.

It gives vision question Q9 something concrete to answer

Q9 asks whether remote or mobile access is in scope. This proposal does not answer it: it is loopback-only.

The idea

One command, the same app in a browser

This proposal adds a second host for the same app. The UI, the chat domain and the tests stay as they are. Only the layer that connects the UI to gentle-shell is new.

$ gentle-shell-web # illustrative name; naming is an open question listening on http://127.0.0.1:<port> → opens the app in your browser

A spike shows it works and what it costs (about 800 new lines, no existing file changed). It also shows what is missing before anyone else should use it.

How it works

  • The renderer calls useBridge(), which returns window.gentle ?? mockBridge. In Electron, the preload script sets window.gentle.
  • In the web host, a small script sets it before the app starts, built from the same createBridge(ipc) the preload uses, with the IPC object backed by a WebSocket.
  • On the server side, the host rebuilds the object graph that src/main/index.ts builds and reuses registerHandlers() unchanged, through thin stand-ins for Electron's IpcMain and WebContents.

Scope

What it is not

Not a terminal in the browser

Issue #2 considers a terminal in a window and says it "defeats the entire point of a plain-chat, minimalist app", keeping it only as "a possible future 'power mode' toggle, not the default". The web host renders the same chat UI, not the TUI.

Not pi's packages/server

Issue #2 marks it "Rejected for now" ("no auth, explicitly marked experimental"). The web host talks to gentle-shell --mode rpc, as the desktop does.

Not a second UI

The UI is not copied or redesigned. If it diverged, this proposal would have failed.

Not remote access

It binds to 127.0.0.1 only. There is no flag to change that.

Not a replacement for the desktop app

People who do not want a terminal at all still need the packaged app (issue #2, "Problem or opportunity").

Limits

What the spike does not prove

Stated here so nobody has to find it out later.

No multi-client behavior

There is one shared ChatHost, so one open chat at a time. This is the existing audit A3, not something the web host adds.

No reconnect or resume

A dropped socket loses the live view.

The child outlives the browser

Closing the tab leaves the gentle-shell child running until the host exits.

Token scrubbed on the client only

The token is scrubbed from the URL only on the client. It stays in browser history and network logs until it is exchanged for a session cookie.

Static assets served without the token

A <script src> cannot carry one. They are inert code; all data goes over the authenticated socket.

Hand-written WebSocket

The ws package was not hoisted in the workspace, so both ends implement RFC 6455 by hand. A parser we maintain ourselves is attack surface we do not need. Replace with ws.

No automated tests for the server's authentication

The checks above ran as scripts. Only the client IPC has unit tests.

No TLS and no rate limiting

Acceptable on loopback, to be revisited before anything else is allowed.

Launcher lookup on Windows needs the spawn fix

The spike only ran with GENTLE_SHELL_BIN pointing at the .mjs entry. Slice 1 fixes it.

Security model

The rules

The model is copied from what gentle-shell already ships for its own install wizard (scripts/installer-server.mjs: loopback bind, a random token compared with timingSafeEqual, same-origin headers, and "the browser never sends commands, paths, plans or environment").

RuleWhy
Bind 127.0.0.1 only; no option to change itRemoves LAN exposure by default
Random 32-byte token per run, constant-time comparisonA page open in another tab cannot call the host without it
Exact Host and Origin match, also on the WebSocket upgradeStops DNS rebinding and cross-site WebSocket hijacking
The browser sends typed operations (the same channels as the IPC handlers), never a command line, path or environmentThe host decides what runs; the page cannot construct execution
Token exchanged once for a session cookie, then removed from the URL Planned, slice 3Keeps it out of history and logs
Child process tied to its connection Planned, slice 3No orphaned agents

A local server in front of an agent with shell access is the real risk of this proposal. If the model above cannot hold, the right answer is to cut scope, not to relax it.

Out of scope

Future work, not part of this proposal

Recorded so it is not lost. None of it is required for the first useful version:

  • Separate sessions per browser client, so two tabs do not share one chat (audit A3, F1 in PR #29).

  • Running /gentle:* commands from the UI.
  • Reconnect and resume; a project-folder picker (audit A10).
