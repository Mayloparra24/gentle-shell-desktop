El problema

Por qué un host web

Elimina el paso de empaquetado en el camino hacia un primer chat

Hoy la aplicación se ejecuta desde el código fuente con Electron. No hay compilaciones firmadas, y solo se ha probado macOS en Apple silicon (README.md, sección "Try it"). Un host en el navegador necesita Node y el lanzador que el usuario ya tiene.

Ayuda a quienes contribuyen a verificar el comportamiento real

El ADR 0010 ya ejecuta el renderer en un navegador, pero contra un puente simulado (mock). El host web lo ejecuta contra sesiones reales.

Hace visible el problema del lanzador en Windows desde un segundo ángulo

En Windows, un gentle-shell instalado con npm se resuelve como gentle-shell.cmd, que Node no puede lanzar directamente. Son las incidencias #23 y #24, y bloquea a ambos hosts por igual.

La idea

Un comando, la misma aplicación en un navegador

Esta propuesta añade un segundo host para la misma aplicación. La interfaz, el dominio del chat y las pruebas permanecen como están. Solo es nueva la capa que conecta la interfaz con gentle-shell.

$ gentle-shell-web # nombre ilustrativo; el nombre es una pregunta abierta escuchando en http://127.0.0.1:<puerto> → abre la aplicación en el navegador

Una prueba de concepto muestra que funciona y cuánto cuesta (unas 800 líneas nuevas, ningún archivo existente modificado). También muestra qué falta antes de que otra persona deba usarlo.

Cómo funciona

  • El renderer llama a useBridge(), que devuelve window.gentle ?? mockBridge. En Electron, el script preload define window.gentle.
  • En el host web, un pequeño script lo define antes de que arranque la aplicación, construido con el mismo createBridge(ipc) que usa el preload, con el objeto IPC respaldado por un WebSocket.
  • Del lado del servidor, el host reconstruye el grafo de objetos que construye src/main/index.ts y reutiliza registerHandlers() sin cambios, mediante sustitutos delgados de IpcMain y WebContents de Electron.

Alcance

Qué no es

No es una terminal en el navegador

La incidencia #2 considera una terminal en una ventana. Cita textual en inglés de la incidencia: "defeats the entire point of a plain-chat, minimalist app"; solo la conserva como "a possible future 'power mode' toggle, not the default" (también cita textual). El host web muestra la misma interfaz de chat, no la TUI.

No es el packages/server de pi

La incidencia #2 lo marca como "Rejected for now" (cita textual en inglés), con la nota "no auth, explicitly marked experimental" (también cita textual). El host web se comunica con gentle-shell --mode rpc, igual que el escritorio.

No es una segunda interfaz

La interfaz no se copia ni se rediseña. Si divergiera, esta propuesta habría fracasado.

No es acceso remoto

Solo se enlaza a 127.0.0.1. No hay ninguna opción para cambiarlo.

No reemplaza la aplicación de escritorio

Quienes no quieren una terminal en absoluto siguen necesitando la aplicación empaquetada (incidencia #2, sección "Problem or opportunity").

Límites

Lo que la prueba de concepto no demuestra

Se indica aquí para que nadie tenga que descubrirlo después.

Sin comportamiento multicliente

Hay un solo ChatHost compartido, por lo que solo hay un chat abierto a la vez. Es la auditoría A3 ya existente, no algo que añada el host web.

Sin reconexión ni reanudación

Un socket caído pierde la vista en vivo.

El proceso hijo sobrevive al navegador

Cerrar la pestaña deja el hijo gentle-shell en ejecución hasta que el host termine.

Token eliminado solo en el cliente

El token se elimina de la URL solo en el cliente. Permanece en el historial del navegador y en los registros de red hasta que se intercambia por una cookie de sesión.

Recursos estáticos servidos sin el token

Un <script src> no puede llevar uno. Son código inerte; todos los datos viajan por el socket autenticado.

WebSocket escrito a mano

El paquete ws no estaba elevado a la raíz del espacio de trabajo, por lo que ambos extremos implementan RFC 6455 a mano. Un analizador mantenido en el propio proyecto es superficie de ataque innecesaria. Reemplazar por ws.

Sin pruebas automatizadas de la autenticación del servidor

Las verificaciones anteriores se ejecutaron como scripts. Solo el IPC del cliente tiene pruebas unitarias.

Sin TLS ni límite de tasa

Aceptable en loopback; debe revisarse antes de permitir cualquier otra cosa.

La búsqueda del lanzador en Windows necesita la corrección de spawn

La prueba de concepto solo se ejecutó con GENTLE_SHELL_BIN apuntando a la entrada .mjs. El tramo 1 lo corrige.

Modelo de seguridad

Las reglas

El modelo se copia de lo que gentle-shell ya incluye para su propio asistente de instalación (scripts/installer-server.mjs: enlace a loopback, un token aleatorio comparado con timingSafeEqual, cabeceras de mismo origen y, en cita textual en inglés, "the browser never sends commands, paths, plans or environment").
